SaaS Mini · Base de datos

Hay una sola base de usuarios (core.sqlite, quince tablas de identidad y cobro) y nueve bases de negocio, una por producto. Cada producto abre la suya con openProductDb() y declara solo sus tablas; el Core abre la central con createCoreDb() y no guarda nada de negocio.

Una base de usuarios, nueve de negocio

  • El Core abre core.sqlite con createCoreDb(): quince tablas de identidad y cobro, y ninguna de negocio.
  • Cada producto abre la suya con openProductDb() y declara solo sus tablas en products/<slug>/src/ddl.ts.
  • Antes era un DDL compartido de 17 tablas para todos; hoy la tabla que un producto no declara, no existe para él.
  • 47 tablas de negocio repartidas: citas 10, espacios 8, checklists 7, solicitudes 5, crm y pagos 4, activos, cotizaciones e inventario 3.

El aislamiento es la base, no el filtro

  • Un archivo SQLite por producto y otro para el Core. Ningún volumen se comparte entre contenedores.
  • organization_id sale siempre de la sesión (SSO) y nunca del cuerpo ni de la query; toda consulta se filtra por él.
  • Un producto no se conecta a la base de otro, y products/* no importa @amg/platform: hablan por HTTP.
  • Lo único que cruza es la identidad, y cruza por SSO con un JWT firmado con el secreto de cada producto.

Migrar sin adivinar

  • journal_mode = WAL y foreign_keys = ON por conexión: las lecturas no bloquean y las FKs sí se validan.
  • En los productos, amg_migrations registra cada migración: corre una sola vez, en su transacción, y corta el arranque si falla.
  • En el Core, MIGRATIONS hace ALTER TABLE … ADD COLUMN idempotente para bases creadas en una versión anterior.
  • Montos y precios en enteros (centavos): sin punto flotante en el dinero.
